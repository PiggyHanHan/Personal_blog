# 一场追了半天的「分区上色不一致」bug：问题根本不在代码里

## 开场：一个"看起来很像代码 bug"的现象

做 7 天藻华预测系统时，用户反馈：

> 分区模式下，分区上色图经常从 day2 / day3 / day4 才开始出现，而且**某天的分区上色图跟当天的图对不上**。不知道是仅仅上色写错了，还是数据本身有 bug。

两个直觉都指向"系统代码有问题"：要么是 `colored_zones.png` 画的时候用错了掩码（上色 bug），要么是分区检测本身算错了（数据 bug）。这正是这类"看起来在代码里"的幺蛾子最经典的开场。

## 关键一步：把"上色 bug"和"数据 bug"拆开

追这种问题，最忌讳一上来就满眼扫代码。我做的第一件事是**拆问题**——上色图由两部分组成：

```
colored_zones.png = 底色（当日掩码上色） + 红线（分区边界）
```

那么"对不上当天图"只可能是：
1. **底色错了**（画的时候用的不是当天的掩码，而是别的天的）→ 上色/时序 bug；
2. **红线错了**（分区边界和当天藻类分布对不上）→ 分区数据 bug。

拆开的方法很朴素：**用当天保存的 `mask.png` 重新上色一遍，跟 `colored_zones.png` 逐像素比对，把红线像素单独抠出来不算**。如果底色完全一致，就说明上色逻辑没问题，问题在别处；如果不一致，且最好地匹配到了**别的天**的掩码，那才是真正的"错位"。

这一招立刻给出答案：某张图的 day7 上色图，底色最匹配的其实是 **day0/origin 的掩码**，而不是它自己的——**它用的是"残留"的旧掩码**。于是嫌疑从"上色逻辑"转移到了"数据来源"。

## 验证方法：把"跑出来的"和"保存的"对一下

为了排除是我比对方式的问题，我又把**当前代码**的 `detect_zones_morph` 对**每一天保存的 mask.png 重新跑了一遍**，跟保存的 `zone_map.npy` 做 100% 匹配率比对：

```
重新分区(当天 mask) == 保存的 zone_map.npy ?
```

- 有的图：每天 **100% 一致**，上色图底色也 **0% 错位** —— 这套数据是干净的；
- 有的图：只有 day0 一致，day1~7 只有 **~73%** 匹配 —— 这套数据是"脏"的。

同样的代码、同样的流程，结果却分成两拨，这本身就是最有力的线索：**出错的数据不是这一套代码跑出来的**。

## 峰回路转：正规入口全对，归档数据全错

于是我用正规入口 `main.py --test --mode forecast --zone-method morph` 单测了 5 张 DJI 影像，结果**全部干净**：

| 检查项 | 结果 |
|---|---|
| 每日 `colored_zones.png` 底色 vs 当日 `mask.png` | 逐像素一致，0% 错位 |
| 保存的 `zone_map.npy` vs 当日 mask 重跑分区 | 100% 匹配 |
| `zone_growth` 是否每天都有 | day0 起就有 5 区，没有"从 day2 才开始" |

"分区从 day2/3/4 才开始"、上色图跟当天对不上——**正规 main 根本复现不出来**。出错的是归档目录里那一批结果，而它们来自一次"临时脚本快速批量跑 24 张"。

## 定位唯一差异变量：n_zones = 5 vs 0

继续对比同一张 DJI_0139 的"正规跑"和"归档跑"origin JSON，发现：分割结果**完全一样**（algae 15.02 m²、density 相同、weather 相同），唯一差别是——

- 归档：`n_zones=0`（`zones=[]`），但 `zone_map.npy` 却是 5 区；
- 正规：`n_zones=5`。

这是个典型的**数据不自洽**：JSON 说没分区，npy 却说有 5 个区。而正是这个差别，让 day 循环走了两条完全不同的预测路径：

```
归档（zones=[]）→ 全局预测，一个大的环境容量 K → 预测增长（day7 ~24.5m²）
正规（zones=5）→ 逐区预测，每区各自的小 K → 部分区近/超容量 → 预测收缩（day7 ~11.6m²）
```

所以"这次跑的 139 怎么跟归档差这么多"——不是 `--all`、不是 `--dla-launch` 变了，就是**归档 origin 的 `zones` 字段为空，逼着走了全局路径**。发射模式只影响空间形态，不影响面积轨迹。

## 顺带踩到的另外一个坑：growth_rate 正数却"在衰减"

排查时我还看到"每区 `growth_rate_d` 都是正数，但 `predicted_area < current_area`"，乍一看自相矛盾。其实不是：

```
growth_rate_d = r     # 这是内在生长率，不是"实际增长"
predicted_N    = N + r·N·(1 - N/K)
```

当 `N > K`（超过环境容量）时，`(1-N/K) < 0`，于是即便 `r` 为正，面积也在**下降**。这是 Logistic 的正常行为，不是 bug。

但这也带出一个值得反问的问题：**带分区的逐区预测普遍"收缩"，无分区的全局预测普遍"增长"**。趋势方向完全相反——那到底哪个才符合物理直觉？这已经不是代码 bug，而是**模型/口径合理性**的取舍，值得单独想清楚。

## 踩坑总结

1. **先分清真 bug 和假 bug。** 表象"像代码 bug"≠代码有 bug。先问一句：这套数据是**正规入口**跑出来的，还是**临时/批量脚本**跑出来的？临时脚本为了快，经常跳过、复用或简化中间产物，结果不自洽，能把人带偏半天。
2. **"重新生成"是对付可视化问题的利器。** 保存的产物对不上，就用当天数据重算一遍跟它对。一致→问题在上游数据；不一致且匹配到别的天→问题在"用了旧数据"。
3. **拆解现象，锁定唯一变量。** 把问题拆成"底色+红线"，再在两组结果里找唯一不同的字段（这里是 `zones` 是否为空）。两侧其余字段全相同，那凶手就只剩这一个。
4. **读代码前先看数据是否自洽。** `zones=[]` 但 `zone_map.npy=5 区`，这种自相矛盾本身就是破案线索。
5. **确定性验证 + 视觉确认。** 既要有逐像素/匹配率的客观数字，也要真的把图打开看一眼（很多"图对不上"其实是人眼对图案的直觉，数字会告诉你真相）。

最后：这类问题**没有改任何生产代码**——因为要修的从来不是代码，而是"下次别再用临时脚本糊弄批量产出了"。

*（注：分区检测目前 DL 权重缺失、默认走形态学；本次所涉均为形态学分区。）*
